# i18n Standards

## Setup

- Library: `next-intl`
- Locales: `ar` (Arabic, RTL, **default**) and `en` (English, LTR)
- Routing: all routes under `app/[locale]/...`
- Config: `i18n/routing.ts` (locale definitions) and `i18n/request.ts` (message loading)

## Translation Files

- `messages/ar.json` — Arabic (must always be complete)
- `messages/en.json` — English (supplementary)

Every key in `ar.json` must also be in `en.json`. The reverse isn't enforced, but aim for parity.

## Translation Key Naming

Use dot-notation with a component or feature prefix:

```json
{
  "nav": {
    "home": "الرئيسية",
    "settings": "الإعدادات"
  },
  "quran": {
    "page": "صفحة",
    "surah": "سورة"
  }
}
```

Keys should be descriptive, not generic. Avoid single-word keys at the top level.

## Using Translations in Server Components

```ts
import { getTranslations } from "next-intl/server";

export default async function MyPage({ params: { locale } }: ...) {
  setRequestLocale(locale); // Always call this first
  const t = await getTranslations("nav");
  return <h1>{t("home")}</h1>;
}
```

**Always call `setRequestLocale(locale)` before accessing translations in async server components.**

## Using Translations in Client Components

```ts
import { useTranslations } from "next-intl";

export function MyComponent() {
  const t = useTranslations("quran");
  return <span>{t("page")}</span>;
}
```

## Direction

Direction is set at the layout level. Use the helper from `app/utils/i18n.ts` to determine `dir`:

```ts
import { getDirection } from "@utils/i18n";
const dir = getDirection(locale); // "rtl" | "ltr"
```

Quran text always needs `dir="rtl"` explicitly, even in an LTR layout.

## Routing Navigation

Use the locale-aware navigation from `i18n/routing.ts` instead of Next.js built-ins:

```ts
import { Link, redirect, usePathname, useRouter } from "@/i18n/routing";
```

## Placeholders: never use the project wrapper

`app/hooks/use-translations.ts` calls next-intl's `t(key)` with **no values**, so it must only be used for keys with **no ICU placeholders**. For a message containing `{placeholder}`, use next-intl's `useTranslations(namespace)` directly and pass the values — as `app/components/reader/ViewingChip.tsx` does. Do not modify the wrapper to accept values, and do not interpolate with `.replace()`.

The failure is silent, which is why this keeps recurring. Client-side, the unfilled ICU pass does not throw: next-intl reports to `onError` (a `console.error`) and returns **the key path**, which then matches the wrapper's `translation === key` "missing key" test, so the wrapper serves its inline English default. An Arabic user sees English copy — the Arabic string never renders, and nothing fails. Server-side the same message is fatal instead: it surfaces as `FORMATTING_ERROR` and fails `next build` during static generation. So a placeholder key evaluated in both places gives a build error in one path and wrong-language text in the other.

Pre-convert numeric values with `toLocaleNumeral` and pass them as **strings**, so ICU substitutes them verbatim and the Eastern Arabic numeral policy is preserved rather than overridden by ICU's own number formatting.

Prior occurrences: `docs/plans/fix-viewing-chip-intl-interpolation.md` (2026-07-07) and again in `docs/plans/pwa-offline-support.md` Addendum 1.

## Extracting New Strings

Run `npm run extract-translations` to sync new translation keys from the codebase into the message files.
