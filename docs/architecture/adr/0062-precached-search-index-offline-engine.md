# ADR 0062: Precached Quran Search Index & Offline Search Engine

**Status:** accepted
**Date:** 2026-09-06
**Epic:** #536 (phase 1: #537 + API half of #538)

## Context

Verse search is online-only: `useSearch` fetches `/api/search/verses` + `/api/search/chapters`,
both Prisma `contains` queries capped at `take: 10`. Offline (installed PWA, no connection) search
shows nothing. The epic wants offline search plus a full-results page; phase 1 is the index, the
offline engine, and API pagination (no UI changes beyond adapting to the new envelope).

A browser experiment (2026-09-06, reverted, no trace in tree) rendered three display candidates
inside `SearchQueryResults` rows: `verse.text_uthmani` (B), `words.text_uthmani` join (C), and
`verse.text_imlaei_simple` in Tajawal (A), against the current `words.qpc_uthmani_hafs` join.

## Decision

1. **Committed static index** `public/quran/search-index.json`, generated by
   `scripts/quran-search-index/generate.js` (`npm run generate:quran-search-index`), following the
   existing `scripts/quran-chapters/generate.js` pattern. One row per verse (6,236):
   `{ "k": verse_key, "t": text_imlaei_simple, "d": pre-joined qpc_uthmani_hafs display string,
   "c": chapter_id }`. Measured 2026-09-06: ~2.4 MB raw on disk (~0.6–0.8 MB gzip wire).
2. **Display column is the pre-joined qpc string, never imlaei/uthmani.** The experiment showed only
   the qpc join renders correctly: imlaei has simplified alif/hamza forms (rejected on sight);
   B/C render pause/waqf codepoints as plain circles under `UthmanicHafs1Ver18` (all codepoints are
   in the font cmap — verified, 0 missing — so this is the font's intended shape for those
   codepoints, not tofu; stripping them would delete real waqf orthography). C additionally needs
   per-word rows, defeating the index's purpose. The generation script joins
   `Word.qpc_uthmani_hafs` in `position` order — the same join the API/overlay uses today, so
   offline rows are pixel-identical to online rows.
3. **The index carries no page number and no chapter names.** `Verse.page_number` is a denormalized
   mirror of the default edition (56 verses paginate differently in other editions; word text itself
   is edition-agnostic, placement lives in `MushafWordLayout`). Page resolves at use time through
   the active edition's precached `verse-pages/{mushafId}.json`; names through the precached
   `chapters.json` (ADR 0033). This keeps the index edition-safe by construction.
4. **Delivery is install-time precache** (`globPublicPatterns` += `quran/search-index.json`):
   offline search works with zero prior online search. Accepted cost: ~0.7 MB added to every
   production visitor's install manifest (lazy-load on intent was considered and rejected for
   failing the first-ever-search-offline case).
5. **Offline engine lives in `useSearch`**: online → API envelope; `navigator.onLine === false` or
   fetch rejection → local index with identical normalization (`normalizeArabicQuery` hamza→alif,
   `normalizeDigits` fold) and identical `take`/`skip` pagination client-side. Chapters offline
   filter the already-precached `chapters.json` (strict `contains` + numeric-id match preserved).
6. **Both search routes migrate to `jsonResponse()`**: `{ data: { results, total } }` with
   `take`/`skip` params (default `take: 10`, server max-`take` 50 — the `Word[]` eager-load is what
   makes the cap load-bearing). The raw `{ results }` shape is removed; `useSearch` and the overlay
   prop-passing adapt in the same change.

## Constraints

- Generation `select`/join MUST stay in sync with `VerseResult` and the index-row contract above;
   the script header carries the sync note like `quran-chapters/generate.js` does.
- `isSearchQueryValid` (≥2 chars) stays enforced server-side and client-side, both paths.
- The match column stays `text_imlaei_simple` with query-only hamza normalization (ADR 0007);
   the display string is never matched against.
- Do not add `page_number` or chapter names to the index later as a "convenience" — that
   reintroduces the cross-edition misnavigation this ADR removes.
- `search-index.json` is immutable content: regenerate + commit on Quran data changes only, same
   as `chapters.json`.

## Consequences

- Phase 2 (#539 + overlay "More results" button) consumes `{ results, total }` + `skip` paging for
   infinite scroll, online and offline, with no further API shape work.
- `e2e/tests/search.spec.ts` 10-cap assertion is unaffected (overlay keeps `take: 10`).
