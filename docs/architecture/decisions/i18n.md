## i18n

**Status:** active

**Decision:** `next-intl` with two locales: `ar` (Arabic, default, RTL) and `en` (English, LTR). All routes are under `app/[locale]/`. Translation keys live in `messages/ar.json` and `messages/en.json`.

**Constraints:**
- Always call `setRequestLocale(locale)` in async server components/layouts before accessing translations.
- Default locale is `ar` — Arabic must always have translation coverage; English is supplementary.
- Direction is determined at the layout level via `app/utils/i18n.ts`.
- **ICU Plurals & Parameter Interpolation (2026-09-10, #610):** Never hand-concatenate counts with fixed plural nouns, and never use `t().replace()`. Use next-intl's `useTranslations(namespace)` directly with parameter objects. In Arabic messages, define full ICU plural categories (`one`, `two`, `few`, `many`, `other`); pass numeric `count` for category selection and a pre-localized string `{n}` (via `toLocaleNumeral(count, locale)`) to render digits, as ICU's `#` defaults to Western digits in generic Arabic (`"ar"`).
- **Date Numeral Localization (2026-09-10, #610):** `toLocaleDateString(locale, ...)` with `locale === "ar"` renders Latin digits for day and year in standard CLDR data. Always format dates with `locale === "ar" ? "ar-u-nu-arab" : locale` so Arabic dates display Arabic-Indic numerals (`١٠ أكتوبر ٢٠٢٦`).
- **No inline locale ternaries (2026-09-11, #599):** Every user-visible string must resolve through `messages/ar.json` and `messages/en.json`. Never use inline `locale === "ar" ? "…" : "…"` ternaries for user-facing copy — not for a single word, not for directional arrows (`←`/`→`), and not for captions. Directional copy must reside in the catalogues so each locale specifies its appropriate reading flow.
- **Mandatory six-category ICU plurals for counting strings (2026-09-11, #599):** Every counting string in `messages/ar.json` must provide an ICU plural object defining all six Arabic plural categories: `zero`, `one`, `two`, `few`, `many`, and `other`. A single `{{count}}` or binary singular/plural interpolation is grammatically invalid in Arabic for 1, 2, 3–10, and 11+ items (e.g. producing "٢ يوماً نشطاً" instead of the dual form "يومان نشطان"). Never use `t(key, default).replace("{x}", v)` — it bypasses next-intl parameter formatting and silently returns the fallback string.
- **Domain-agnostic UI primitives must not translate (2026-09-11, #600):** Components in `components/ui/` are domain-agnostic primitives and must not call `useTranslations` or reference translation keys directly. All localized copy, empty-state text, and placeholders must be passed in as props by the consuming screen that owns the domain context.
- **No static gate catches missing i18n keys (2026-09-11, #599, #600):** Neither ESLint, TypeScript (`tsc`), Vitest, nor Playwright will detect a missing, misspelled, or mismatched translation key; runtime resolution failures throw `MISSING_MESSAGE` in production and flood the browser console. Every i18n addition or refactor requires an explicit key-resolution audit ensuring the exact key path exists in both `messages/ar.json` and `messages/en.json`, verified by opening the affected surface in the browser and inspecting the console.
