## Awrad & Learning Plans Engine

**Status:** active

**Decision:** Daily awrad and structured programs (الحصون الخمسة) run on one plan engine: plan templates are typed TS constants (like `MARK_CATEGORIES`), each template composed of tracks; a track = unit + quantity + one of five typed scheduling rule kinds (`fixed_cycle`, `cursor_advance`, `trailing_window`, `completed_cycle`, `lookahead`) + a per-track `activity` (`read | listen | memorize | review`). Only enrollments (`UserPlan`) and an append-only `ProgressEntry` log are stored (in `furqan_app`); the daily assignment is derived at read time as a pure function of (template, params, progress, date) — never persisted. See [ADR 0030](../adr/0030-plan-engine-derived-assignments.md) and `docs/plans/awrad-learning-plans.md`.

**Constraints:**
- Progress unit is **per-track**, `"page"` or `"verse"` (widened by [ADR 0038](../adr/0038-plan-engine-per-enrollment-verse-unit.md), `docs/plans/awrad-verse-granularity.md`) — each independent (`fixed_cycle`/`cursor_advance`) track's unit is chosen at enroll time via `params.trackUnits` and never migrated mid-plan; a dependent track (`trailing_window`/`completed_cycle`/`lookahead`) always inherits its `sourceTrack`'s resolved unit rather than choosing its own, since its range math slices that source's own logged numbers directly. juz/hizb/rub targets still resolve to page ranges from seeded `PageMetadata`/`Rub`, then convert to verse ordinals for a verse-unit `cursor_advance` track via the static `app/lib/plans/verse-index.ts` (no DB calls, no cross-domain FK). Existing page-unit rows are untouched — no bulk data migration.
- All new tables live in `furqan_app` with scalar Quran refs only — no cross-domain FK (ADR 0008 invariant holds).
- Do not materialize schedule rows ("day X → range Y" tables) — pause/skip/level-change safety depends on derivation. History views read the progress log (what was actually done), never recompute assignments with current params.
- `activity` is per-track, orthogonal to scheduling — never encode modality into rule kinds or templates as a whole (a template may mix, e.g. a listen-mode تحضير track).
- Missed-day policy is a per-template flag: cursor-shift (default) or calendar-bound (recompute daily quantity toward a fixed end date). Streaks derive from the log.
- Completion is manual per-track check-off; reader/playback-aware shortcuts may *offer* check-off but must never auto-write it.
- Multiple concurrent enrollments per user are allowed — "today" UI aggregates across active plans.
- Plan check-offs are online-only in v1 (mirrors marks, ADR 0014); offline queueing would need that decision re-opened.
- A rule kind with a `sourceTrack` may only reference a source-free track (`fixed_cycle`/`cursor_advance`) — the engine (`app/lib/plans/engine.ts`) resolves dependencies in two passes, not a general graph. Honor this shape when authoring templates in `app/constants/plans.ts`.
- Unit tests: `vitest` (`npm run test`), introduced with this feature — the repo's first unit-test infra. Tests are colocated `*.test.ts` files with explicit `vitest` imports (no globals config); `vitest.config.ts` carries only the `@/` alias. Scope is pure functions (the engine); API routes/hooks are wiring and stay covered by e2e/integration, not unit mocks.
- UI (hub page + reader widget, Trello #149): `listening-wird` and `husun` templates ship alongside `daily-wird` (extended 2026-09-09 by #607 to include `memorizing-wird` and `reviewing-wird`; see below). Husun's per-track quantities are a documented **best-effort default**, not a sourced book table — this deliberately supersedes the foundation plan's "husun waits for sourced quantities" gate; every quantity is editable at enroll time via `params.quantities`, so a correction needs no deploy. Its hifz (`cursor_advance`) pace is a free numeric quantity input (pages, verses, or a fractional-page pace — ADR 0038) — no preset levels; its target range is picked via two juz dropdowns and resolved to page numbers server-side inside `POST /api/plans` (reusing `resolve-units.ts`'s `getJuzPageRange`), never exposed as a separate endpoint and never stored as juz numbers. That same POST is where client-supplied `params` get validated (page bounds, positive-integer quantities) — the engine trusts its inputs. Teacher-assigned levels are explicitly out of scope (no ADR 0012 grant wiring for plans yet). The reader widget determines per-track "in range" state by comparing the assignment's page range against the reader's **visible pages** (`read`/`memorize`/`review`) or `RecitationContext`'s `recitedPage` (`listen`, while a session is live). Visible pages are newly published by `ReaderPager` to a small `ReaderPageContext`, following the publish-up pattern `RecitationPageSync`/`pageFirstVerseKey` established for the voice panel — and as a pair-expanded **array**, not the pager's raw `anchor`, since double-page/tablet view shows two pages (same `getPagePair` expansion `RecitationFollow` already uses). See `docs/plans/daily-awrad-ui.md`.
- **Companion visual redesign (2026-07-28):** the hub/widget UI above was reshaped around a Claude Design reference (`docs/plans/daily-awrad-ui.md`'s "Companion Redesign" section) into a hero "today" card, timeline-style plan history, a consolidated browse-or-edit dialog, and a ring check-off control, adding two new derived capabilities on top of the same engine. **Streak/week-strip** (`app/lib/plans/streak.ts`, `GET /api/plans/streak`): derived at read time like assignments themselves (never persisted) by replaying `deriveAssignments` against past dates for the caller's currently-active plans only — a day with zero assignments due is a pass-through, not a failure, and a plan's pause/resume history isn't reconstructed (no status-change timestamps exist), an accepted limitation. **Plan param editing**: the existing `PATCH /api/plans/:planId` now also accepts optional `params`/`target_juz_start`/`target_juz_end` (full replace, not merge) — the juz-resolution + params-hardening logic that used to live only in `POST /api/plans` was extracted to `app/lib/plans/validate-params.ts` and is shared by both. `GET /api/plans` additionally returns derived `target_juz_start`/`target_juz_end` (via a new `getPageJuzNumber` reverse lookup in `resolve-units.ts`) purely to prefill the edit UI — juz numbers are still never stored (D3 holds).
- **Invariant (bug fix, 2026-07-28):** once a track has a progress entry logged for the queried date, `deriveAssignments` must return that entry's own range verbatim (`app/lib/plans/engine.ts`'s `todayEntryAssignment`) — never recompute a cursor/window position for an already-logged day. Previously the range was derived independently of the date-based `completed` flag, so checking off any *other* track in the same plan (which invalidates the whole `["/plans"]` query) silently advanced an already-checked track's shown range to the next not-yet-done position while it stayed marked completed. Applies uniformly to all five rule kinds; any future rule kind must honor it too.
- **Inline listening playback (2026-07-30):** any `activity: "listen"` row (listening-wird's own track, and husun's `tahdeer` track) plays its assignment's exact page range directly via `RecitationContext.play`'s new override argument, instead of only linking to the reader (which is what the foundation plan's Verified Test Case #3 originally envisioned). Bounds are resolved via the existing `GET /api/quran/pages/[pageId]/bounds` route (ADR 0033's edition-aware page-bounds endpoint, originally built for the "custom" stopPoint's page-type "to" target), extended to also return `firstVerseKey` alongside its existing `lastVerseKey`/`lastChapterId` — a wird's `rangeStart`/`rangeEnd` are always resolved against `DEFAULT_MUSHAF_ID`, since plan assignments are page-canonical from before mushaf editions existed (D3 predates ADR 0033), not the reader's currently-active edition. A track's `repetitions` (e.g. husun tahdeer's `×10`) means whole-range repeat, not per-verse repeat. A page's first/last word can belong to a verse that starts on the previous page or ends on the next — `/bounds` resolves the owning verse regardless, since recitation audio is addressable per verse, never per word, so consecutive wird days can overlap by at most one verse at each seam (accepted: better a repeat than a gap). See `docs/plans/listening-wird-inline-playback.md` and the Recitation Playback decision above for the `play()` override mechanism itself. The completion nudge/check-off prompt is deliberately deferred (Trello #161) — completion is still manual-only per-track check-off, unchanged. **Settings-sheet indicator (2026-07-30, prompted by manual testing):** `RecitationContext` exposes `activeOverride: { id, label } | null`, set/cleared alongside `rangeRepeatOverrideRef` (including on `stop()` and on a failed `play()`, both previously left it stale) — `RecitationSettingsSheet` shows it as a read-only "Playing: {label}" banner when non-null, since the sheet otherwise always renders the user's own persisted settings with no indication a wird override is actually driving playback. Informational only — every control below it stays exactly as interactive as before. `PlanAssignmentRow` keys its own play/pause state off `activeOverride.id === planPlaybackSessionId(planId, trackKey)` (`app/lib/plans/assignment-range.ts`), not a page-range overlap — a page overlap alone doesn't mean the override was launched by that row.
- **Daily-wird activity flavours (2026-09-09, #607):** the daily-wird preset is reframed from two standalone templates into four activity flavours: `daily-wird` (read), `listening-wird` (listen), `memorizing-wird` (memorize), and `reviewing-wird` (review) — all single-track `fixed_cycle` over pages 1–604 with `missedDayPolicy: "cursor"`. Presented in the UI as one unified concept "Daily wird — <activity>" with an activity sub-picker (`read` → `listen` → `memorize` → `review`). The two original template keys (`daily-wird`, `listening-wird`) remain verbatim with zero schema changes or migrations, keeping existing enrollments and progress logs valid. Default paces for new flavours mirror Al-Husun Al-Khamsa: `memorizing` → 1 page/day (husun `hifz`), `reviewing` → 1 page/day (husun `baeed`); `read`/`listen` stay at 5 pages/day. The `/plans` dialog top-level is now a 3-way wird-type picker (Daily wird, Custom wird [activated in #610], and Al-Husun Al-Khamsa).
- **`params.startPage` semantics (2026-09-09, #607):** `params.startPage` is canonically a mushaf page number (1–604), never a raw verse ordinal. By construction, only the four daily-wird `fixed_cycle` templates send it. `app/lib/plans/validate-params.ts` bounds it to 1–604 regardless of the track's unit; `app/lib/plans/engine.ts` converts it to `pageFirstVerseOrdinal(startPage)` when the track unit is `verse`, resolving a latent bug where a verse-unit `fixed_cycle` track treated `startPage` as a verse ordinal (e.g. page 10 → verse 10 instead of verse 65). Wrap-around khatma behavior (`start > boundEnd`) continues to wrap to page 1 / verse 1. `startPage` is ignored once the track has any logged progress (`state.lastEnd !== null` takes precedence) and is locked in the edit UI; if the effective start page is 1, `startPage` is omitted from `params` rather than written.
- **Custom-wird stored definitions & engine derivation (2026-09-09, #608):** user-authored single-track plans store their canonical definition (`activity`, `unit`, `rangeStart`, `rangeEnd`, `cadence`) directly in `UserPlan.definition` (JSON) alongside optional `UserPlan.name`, selected via `template_key = "custom"` ([ADR 0067](../adr/0067-custom-wird-stored-definition.md)). At read time, `planTemplateFromDefinition` generates a standard `PlanTemplate` with track key `"custom"`, deriving `cursor_advance` for `memorize` and `fixed_cycle` with `onComplete: "stop"` for `read`/`listen`/`review` — pure derivation with zero DB calls inside the engine. `fixed_cycle` tracks gain `boundsUnit` to prevent double-converting already-canonical verse ordinals, and support repeat count K (`repetitions`) under deadline cadence (`missedDayPolicy: "calendar"`), dynamically spreading remaining units across all uncompleted passes. Completion is strictly write-isolated: `POST /api/plans/[planId]/progress` transitions `user_plans.status → "completed"` upon logging the terminal portion, and `DELETE /api/plans/[planId]/progress` symmetrically reverts to `"active"` if progress falls below completion. The engine remains 100% pure and write-free, omitting exhausted custom plans from today assignments.
- **Custom-wird enrollment & edit API (2026-09-09, #609):** user-authored plans resolve from four UI range modes (`surah`, `juz`, `page`, `verse`) into canonical page numbers (1–604) or verse ordinals (1–6236) at enrollment time (`POST /api/plans`), storing `UserPlan.name`, `definition`, and derived `params.trackUnits = { custom: unit }` (`params.endDate` synced for deadline cadence only; `params.quantities` omitted to preserve definition as single source of pace truth). Range modes cannot be mixed. Surah range resolves via scalar aggregate on `quranPrisma.verse` (`chapter_id: { gte, lte }`, `_min`/`_max: page_number`) without cross-domain foreign keys (ADR 0008); verse range resolves statically via `app/lib/plans/verse-index.ts` from verse keys ("surah:ayah") or ordinals (1–6236). Cadence supports daily pace (positive integer), weekly pace (page-unit only, stored as fractional `amount / 7` and floored to >= 1 page/day by engine derivation; rejected for verse units), or calendar deadline (with optional K repetitions, K > 1 rejected for `memorize`). In `PATCH /api/plans/:planId`, `name` and `cadence` are fully editable; `activity` and `unit` are permanently frozen (ADR 0038); `range` is editable only while zero progress entries exist (`progressCount === 0`) and frozen once progress has been logged to preserve `engine.ts` cursor continuity (`state.lastEnd + 1`), never mutating the progress log (ADR 0030).
- **Custom-wird creation & edit UI (2026-09-09, #610):** user-authored wirds author and edit their definition via a dedicated two-decision form (`CustomWirdForm.tsx`, decoupled from `PlanEnrollForm.tsx`'s preset template state), rendered inside a widened dialog (`w-[calc(100vw-2rem)] sm:max-w-lg`) with `fq-scroll-nice`. Unlike preset templates (which operate on a one-slot-per-template model via `activePlanFor`), custom wirds are explicitly multi-instance: the catalog browse picker "Custom wird" card always renders a fresh blank form, while card edit buttons route to their specific instance via an `initialPlan` prop on `PlansBrowseDialog`. To freeze range inputs synchronously upon opening edit mode without a network waterfall, `UserPlanListItem` exposes `has_progress: boolean` (derived in `GET /api/plans` and returned by `PATCH /api/plans/:planId` via Prisma `_count: { select: { progress: true } }`). All page (1–604) and ayah pickers use a searchable `NumberCombobox` (44px touch targets, Western and Eastern Arabic numeral search) instead of raw number inputs. The form renders a real-time display-only preview line calculated purely client-side (`app/lib/plans/custom-wird-estimate.ts`), deliberately duplicating a slice of `engine.ts` math (pace duration and deadline daily pace, backed by colocated unit tests) to guarantee zero latency and offline capability. Surah and juz bounds resolve against static assets (`juz-starts.json` and chapter metadata) with safe fallback to `1` when metadata is loading/unavailable. Human verse ranges are formatted via shared `formatVerseRange` (`app/lib/plans/ui-helpers.ts`) with surah names and localized numerals (`"النساء ١–١٢"` / `"An-Nisa 1–12"`, cross-surah, single-ayah) across `PlanAssignmentRow` (hub hero + reader widget) and `MyPlansList` summary, dropping the redundant `{activity} ·` prefix when `planName` is present. Custom plan names flow through `GET /api/plans/today` (`TodayPlanAssignments.name`) to `PlanAssignmentRow`, `PlansWidget`, and `PlansTodayHero`, backed by `PLAN_TEMPLATE_UI.custom` and `PLAN_TRACK_UI.custom`. All count+unit labels and estimate previews use next-intl ICU plurals (`{count, plural, ...}`) with numeric `count` for selector logic and pre-localized `{n}` for Arabic-Indic numerals, and date displays force `ar-u-nu-arab` for proper numeral localization.
- **Reader wird check-off shortcut & ephemeral widget lifecycle (2026-09-10, #597):** the floating reader widget (`PlansWidget`) is refined from an omnipresent daily-summary pill into an unobtrusive, page-scoped check-off shortcut. It renders `null` unless on a self-reader route with an authenticated session and ≥1 active, uncompleted today-assignment overlapping the current position (`visiblePages`, or `recitedPage` while a listen session is active) — or while its sheet is open, or during a completion flourish. The heavy 50px solid disc and numeric badge are replaced with a ~42px progress dial carrying a quiet ~7.5px centered label ("wird"/"ورد", `aria-hidden`) on a fully opaque card face (`hsl(var(--card))` + `border-border` + a universal inset `--surface-rim` catch-light `box-shadow: inset 0 1px 0 hsl(var(--surface-rim) / var(--surface-rim-alpha))`; near-white on light/gold, a warm step on dark; no glass, no drop shadows, ADR 0032). Indicator displays a continuous 3px ring ($N=1$), segmented arcs separated by ~8° seams ($2 \le N \le 4$, clockwise from 12 o'clock in both LTR and RTL; at-rest stroke `hsl(var(--primary) / 0.6)`), or a proportional arc ($N > 4$) reflecting page-relevant tracks only. Tapping always opens the bottom sheet scoped to page-relevant assignments via shared `PlanAssignmentRow` with a link to `/plans`. The sheet never auto-closes on completion. While the sheet remains open, the widget stays mounted; upon closing the sheet after completing all page-relevant assignments (or immediately if completed with sheet already closed), a brief completion flourish plays (arcs seal solid `--primary`, ~1.05 scale pulse for 1.2s, center label remains visible, shortened for `prefers-reduced-motion`) followed by a 300ms fade-out and unmount; page turns unmount immediately. To prevent controlled Radix `<Sheet>` state latching across unmounts (navigating away unmounts the widget without firing `onOpenChange`, leaving `sheetOpen=true` and causing the sheet to spontaneously reopen upon navigating back), `setSheetOpen(false)` is explicitly called in the lifecycle effect's page-turn branch. Lifecycle transitions use `useIsomorphicLayoutEffect` to commit flourish states before browser paint, eliminating 1-frame unmount blinks. The `/plans` hub remains the sole all-day overview surface.
