## Zone: reader (`app/[locale]/pages/[id]/page.tsx` + `app/[locale]/mushaf/[grant]/pages/[id]/page.tsx`)

```
(page — server component; self reader is statically generated, grant reader is dynamic)
  ReaderPage                 — thin async SSR entry (ADR 0028) shared by both routes (self = statically generated, grant = dynamic); takes basePath + optional grantId/viewingOwnerName. Fetches ONLY the current pair's words (getPageWords ×2, SEQUENTIAL per ADR 0013) and hands off to <ReaderPager>. The old 3-panel (was 5) carousel + buildPanel is gone; every subsequent page change is client-side in the pager (no router.push, no per-swipe remount)
    ReaderPager              — "use client" persistent pager (ADR 0028), mounts once and never remounts. Holds `anchor` page state; renders a keyed 3-panel window [nextAnchor][anchor][prevAnchor] resting at translateX(-100%) so a drag reveals the real prefetched neighbor. Seeds the SSR pair into React Query; fetches/prefetches neighbor content JSON (public/quran/pages/{mushafId}/{n}.json via usePage, keyed per edition) on demand, in TWO stages (ADR 0034): Stage A warms the ±1 window on every anchor settle, and Stage B — gated on Stage A's JSON prefetches AND `pageFontsReady` for the window's fonts — warms the page one step beyond the window in the last-committed direction (tracked in a `lastDirection` ref set by animateCommit, defaulting forward; skipped mid drag/commit). One turn of lead is less than one turn costs on 3G (~167KB of font per double-view turn), so Stage B buys the second turn; issuing both at once would just make the nearer page land later. `stepAnchor(from, goNext, isDouble)` is the shared next/prev-anchor math behind both the live window and Stage B's second step. commitTo swaps `anchor` and re-centers atomically with flushSync (one paint — no recenter flash, see fix-safha-swipe-flicker); animateCommit resolves the physical next/prev neighbor and commits, sliding first ONLY when its `animate` arg is true — the slide exists to continue a drag's live transform, so swipe passes true while the arrows and keyboard pass false and fall into commitTo directly (the same branch prefers-reduced-motion takes). Gated on input source, never on breakpoint: the arrows render from md, so an isLgUp gate would leave tablet arrow-taps sliding and would kill swipe motion on touch laptops; URL synced via history.replaceState (NOT router.push, so usePathname does NOT update — recitation follow must not read pathname). Owns ALL in-reader navigation: swipe, in-spread arrows (QuranSpread.onNavigate intercepts plain clicks; modified/middle clicks fall through to hrefs for SSR/no-JS), physical ArrowLeft/ArrowRight keys (a window keydown effect calling animateCommit with animate=false — ArrowLeft always forward/nextAnchor, ArrowRight always backward/prevAnchor, locale-independent; skipped when a text input/contenteditable has focus, a modifier key is held, or the event is an OS key-repeat — the e.repeat guard replaces the rate limit the removed slide used to provide, so a held key flips exactly one page; see docs/plans/arrow-controls-desktop.md; a keypress while isCommitting is no longer skipped but QUEUED, see below), and recitation follow (followTo). **Input arriving mid-commit TAKES OVER, it is not dropped** (Trello #153, ADR 0028 Addendum 2 2026-08-11): `animateCommit` stores its EXIT_MS timer as `inFlight` ({timer,target}) — the previously unstored setTimeout is why input had to be discarded — and `settleInFlight()` lands that turn immediately (settle, never abort: the user carried it past the threshold). The caller then RE-ENTERS through its own ref (`navRef` for absolute targets, `stepRef` for directions) instead of falling through, because commitTo's flushSync re-renders synchronously and the calling closure still holds pre-settle anchors; the fresh closure sees inFlight cleared so it cannot recurse. Swipe count equals page count on every path (measured 1/2/3/5 swipes → 1/2/3/5 pages). Consequently onTouchMove/onTouchEnd are byte-identical to their pre-#153 form — no queue, no microtask, no latch. `e.repeat` stays ahead of the takeover or a held key turns a page per OS repeat. jumpTo CANCELS an in-flight turn (an edition switch relocates by verse, and the timer would otherwise overwrite the re-anchor 300ms later); the unmount effect cancels it too (it would otherwise fire post-teardown and rewrite the URL); recitation follow deliberately does NOT take over, since truncating a reader-initiated turn would have playback fight the finger. onTouchCancel resets the drag state so a cancelled touch cannot wedge followTo or the Stage B lookahead. Strip onClick toggles NavOverlayContext; reads QuranSafhaViewContext + useIsLgUp to size the window unit (single page vs pair). Computes two id sets and passes both to FontFaceInjector: `allPageIds` (pair-expanded, for tajweed's CSS-only keyed styles) and `baseFontIds` (`allPageIds` only when `isDouble`, else just the single window ids — the eager FontFace registry, unlike CSS `@font-face`, downloads regardless of render state, so it must never include an invisible spread partner; ADR 0029's Addendum). Renders FontFaceInjector + RecitationPageSync + RecitationFollow + MushafSwitchSync + a <link rel="preload"> for the current page's WOFF2 (from the active edition) + the panel strip. Only seeds the SSR pair when mushafId is the default edition — the server renders that edition, so seeding under another edition's key would pair its font with the default edition's word placement (ADR 0033). Publishes its `jumpTo` into ReaderNavigationContext for the duration of its mount (registered/cleared via useEffect) and, once on mount only, compares the real `window.location.pathname` against its own SSR-seeded `initialPage` — a mismatch means the service worker's offline-navigation `setCatchHandler` fallback served this instance in place of a failed navigation, so it self-corrects via `jumpTo` to whichever page was actually requested (or the last-read page, for a fallback with no page in its URL at all, e.g. a failed `/`) (ADR 0014 Addendum 3). The locale prefix is stripped from both the pathname and `basePath` before matching, so a remount where the URL still names the old locale (a locale switch) still recovers the page id instead of falling through to the last-read branch; and that fallback reads `lastReadPage` from `storage`, not LastReadPageContext, whose provider has just remounted to its hydration default of 1 at that instant (#288) That comparison runs in a LAYOUT effect (useIsomorphicLayoutEffect), not useEffect — effects run after paint, so as a plain effect it showed page 1's words before jumping (the "brief page-1 flash" ADR 0014 Addendum 3 had accepted); jumpTo is synchronous, so a layout effect re-anchors in the same frame and page 1 never reaches the screen (ADR 0042). Its strip wrapper carries `.fq-reader-pager-viewport` and each Panel `.fq-reader-panel` — marker classes only; on the mobile/tablet breakpoints globals.css makes the wrapper `position: fixed; inset: 0` so the whole reader's height resolves from the initial containing block and no box below it reads a viewport unit (ADR 0044). Height reaches the card by `align-items: stretch` (the mobile chain centres by default, so the spread container, `.fq-spread-col` and `.fq-full-safha` each need correcting) — never by `%`, which resolves to `auto` inside a flex-grown box and collapses the card
      Panel                  — memo'd: one full-width QuranSpread for an `anchor`, client-fetching its pair via usePage; keyed by anchor so on commit React MOVES the revealed neighbor's DOM into the center slot instead of re-rendering it (the no-flicker recenter — requires a stable onNavigate). Renders QuranSpread unconditionally, passing `lines`/`pageMetadata` as null until its (prefetched) data arrives — the spread then shows QuranSafha's own loading state, so a commit onto an uncached page is never a blank reader (ADR 0034). It previously rendered an empty div here, which on 3G left the reader blank for the whole fetch. Because the loading state is the real card, a loading panel is exactly as tall as a loaded one, which is what keeps #157 fixed (a taller placeholder toggles the scrollbar and reflows the document)
    FontFaceInjector           — "use client" leaf, takes two id-list props: `pageIds` (pair-expanded, drives tajweed's keyed `<style>` LRU) and `baseFontIds` (visibility-scoped, drives the immutable page-font-registry — app/utils/page-font-registry.ts, ensurePageFonts; ADR 0029). Never mutates a live `<style>` (a live stylesheet mutation resets every already-loaded FontFace in it to `unloaded`, blanking visible text — the root cause of the swipe-commit flicker). Tracks two independent rolling LRUs (MAX_KEPT=24 each, one per prop, via a shared `useLruIds` hook backed by `useState`, not a ref — the LRU list must never be mutated outside React's render contract) since the two lists can diverge — e.g. a single-page-view session keeps a page's tajweed style mounted (pair-expanded, cheap CSS) while excluding its spread partner from the eager base-font registry (ADR 0029's Addendum). Client component to avoid RSC resource-hoisting hydration mismatches (ADR 0020). Reads QuranMushafContext itself — only when the active edition `usesColorGlyphs`, renders one immutable keyed `<style key={id}>` per page id (COLRv1 @font-face + @font-palette-values light/dark/gold blocks, family and URL both from the edition registry; ADR 0023). Skips the FontFace registry entirely for a colour-glyph edition, so page fonts are never downloaded twice — React mounts/unmounts whole elements on LRU change rather than rewriting a shared sheet. --Light and --Gold palettes remap brand colors per CPAL slot (Addendum 13); --Dark retains base palette 1 without overrides pending dark-theme color review
    platform.ts               — client-only util (app/utils/platform.ts): isStandaloneDisplayMode() (moved here from use-pwa-precache.ts — the single shared check every offline surface, ContinueReadingLink, and AndroidBackExitGuard must import rather than re-deriving) and isAndroid(). public/launch.html is the one place that necessarily duplicates the display-mode list, since it runs before React and cannot import — re-check it whenever the manifest's `display` changes (ADR 0042)
    overlay-back-guard.ts     — client-only util (app/utils/overlay-back-guard.ts, ADR 0043): module-level armed count (armOverlayBackGuard/disarmOverlayBackGuard/isOverlayBackGuardArmed) tracking whether a useCloseOnBackGesture overlay guard is currently armed. AndroidBackExitGuard checks isOverlayBackGuardArmed() first in its popstate handler and defers entirely when true
    use-is-standalone-mobile-or-tablet — client hook (app/hooks/use-is-standalone-mobile-or-tablet.ts, added with ADR 0043): useIsStandaloneMobileOrTablet() = `!isDesktopUp && isStandaloneDisplayMode()`, the half of the platform gate shared by useCloseOnBackGesture and AndroidBackExitGuard (which further ANDs isAndroid())
    use-close-on-back-gesture — client hook (app/hooks/use-close-on-back-gesture.ts, ADR 0043, Navigation API branch ADR 0045): useCloseOnBackGesture(open, onClose) — on mobile/tablet installed PWA (Android or iOS, not desktop, via useIsStandaloneMobileOrTablet), pushes one fresh, uniquely-id'd (`fqOverlayGuardId`) history guard entry while `open` and calls `onClose` on the next real back-gesture instead of letting it navigate past the overlay; used by MarkModal, SettingsSidebar, the surah Sidebar, NavOverflowMenu, and RecitationSettingsSheet — every one of the app's modal overlays. Where `window.navigation` is supported (modern Android Chrome/Samsung Internet, iOS 26.2+), the close-on-back-gesture and the coordinating echo-swallow are handled via the `navigate` event + `event.intercept()` instead of `popstate` — matched to the guard's own pushed entry by `NavigationHistoryEntry.key`, not `getState()` (unreliable in on-device testing) — and also intercepts a distinct, non-user-initiated `navigationType: "reload"` event the browser can fire ~6ms after the traversal, which is the actual source of a hard-refresh flash `popstate`-based code structurally cannot prevent (ADR 0045). Everywhere else, falls back to the original `popstate`/`pushState` mechanism, unchanged. If the overlay closes another way while its guard entry is still the current top of history, the hook pops it itself (swallowing the resulting echo) to keep the back-stack clean; if something else already navigated past it first — including a sibling overlay opening in the same React commit and pushing its own entry over this one — the entry is left as a harmless orphan rather than pop the wrong one. The "still on top" check is deferred to a microtask and compares by id, not just the shared `fqOverlayGuard` shape (ADR 0043's 2026-08-15 addendum) — a synchronous, shape-only check let one overlay's cleanup pop a sibling's freshly-pushed entry and close it by mistake, reproduced via NavOverflowMenu's Settings row (closeMenu() + setSettingsOpen(true) in one commit). The hook returns `{ notifyNavigating }` (ADR 0043's 2026-08-16 addendum): callers whose close is caused by a `<Link>` navigating inside the overlay call it before closing, so the cleanup skips the still-on-top check entirely instead of racing Next's own (not-guaranteed-synchronous) `pushState` for the target route — applied in BOTH the Navigation API and popstate-fallback branches (the race exists in each independently), so it covers the same platform ADR 0045's `navigate`-based branch now serves. NavOverflowMenu wraps the single `onNavigate` prop it passes to SharedMushafLink/UserMenu with it (so it also fires, harmlessly, from Sign in/Sign out — no competing `pushState` there either); the Settings row calls `closeMenu` directly, bypassing `onNavigate` entirely, and is unaffected
    page-font-registry.ts     — client-only util (app/utils/page-font-registry.ts): the immutable FontFace registry behind ADR 0029. `ensurePageFonts(ids, edition)` creates `new FontFace(edition.fontFamily(id), edition.fontUrl(id)) → document.fonts.add → face.load()` for each unregistered id, keyed by edition AND page since a page number is not unique across editions (ADR 0033) and never modifies a face after creation; a shared module-level LRU (cap 24) evicts via `document.fonts.delete(face)` on the single oldest face only. Called from FontFaceInjector's `baseFontIds` effect (both mobile and desktop/tablet funnel through that one call site for the visible window) and from ReaderPager's Stage B lookahead, the one deliberate exception — never call `.load()`/`ensurePageFonts` for any other id that isn't confirmed visible, since unlike CSS `@font-face` it downloads eagerly regardless of render state. Also exports `pageFontsReady(ids, edition)`: read-only, registers nothing, settles when the already-registered faces for those ids finish — Stage B waits on it so lookahead never competes with the visible window for bandwidth (ADR 0034).
    MushafSwitchSync           — "use client" null leaf: when the mushaf edition changes, re-anchors the pager to the page holding the SAME verse in the new edition (56 verses sit on a different page between editions), resolved via the target edition's verse-pages map. Captures the verse before the new edition's data lands — effect declared before the verse-tracking effect so the switch reads the outgoing edition's verse, not the incoming page's. Keeps a playing verse on screen across a switch (ADR 0021, ADR 0033)
    AndroidBackExitGuard       — "use client": Android + standalone/fullscreen + mobile/tablet only, and only when `active` (excludes the shared-mushaf grant reader, mirroring LastReadPageSync's /mushaf/ exclusion). On mount, pushes one history guard entry; each intercepted back press while unarmed re-pushes it and shows ExitToast, arming a 2s window; a second press within that window skips the re-push and calls window.close() (best-effort). Never lets a real back navigation reach whatever is genuinely behind it while mounted — see ADR 0040 for why a single pushed entry isn't sufficient. Every push allocates a FRESH state object (`guardState()`) and omits the `url` argument: Next's history patch mutates the object it is given, so a shared constant froze a stale router tree and made later pushes bypass the router sync, which the pager's `replaceState` then restored as the wrong locale and page (#288, ADR 0040 addendum). Its popstate handler's first check is isOverlayBackGuardArmed() (ADR 0043) — defers entirely to an open overlay's own close-on-back guard when one is armed, relying on mount order (this guard always mounts first) rather than event-timing
      ExitToast                — "use client": transient bottom-anchored "Press back again to exit" notice, shown only while AndroidBackExitGuard is armed; not dismissible, hides itself on disarm (timer expiry or exit)
    RecitationPageSync         — "use client" null leaf: syncs the current page's firstVerseKey into RecitationContext.pageFirstVerseKey, and its plain page number (in the active edition) into RecitationContext.currentPageNumber, via useEffect; bridges both to RecitationPlayerBar's play button and RecitationSettingsSheet's "custom" range picker (neither can receive props from the pager)
    ReaderPageSync             — "use client" null leaf: publishes the pager's visible page(s) into ReaderPageContext.visiblePages via useEffect (pair-expanded when isDouble, mirrors RecitationFollow's expansion), clearing on unmount; lets PlansWidget compare a track's assigned page range against what's actually on screen
    RecitationFollow           — "use client" null leaf (ADR 0028): the ONLY reader piece that subscribes to RecitationContext's per-word state — isolated here so ReaderPager never re-renders on a recited-word tick (that caused per-word flicker + repeated font re-fetch). Watches recitedPage while status==="playing"; when the recited page leaves the visible window it calls the pager's followTo, DEFERRED via queueMicrotask so it runs after commitTo's flushSync unwinds (an inline commit would be guarded-out mid-flush and never retry). Effect: playback keeps the recited page on screen — swiping away snaps back to it
    QuranSafhaViewToggle      — client pill (lg+ only): single/double icon buttons, reads/writes QuranSafhaViewContext. Rendered from SettingsSidebar, not the reader entry
    QuranSpread              — client (rendered by Panel): houses the two-page layout; receives onNavigate from the pager and wires it into its NavigationArrow pair — a plain arrow click calls onNavigate (pager-driven, no route change), while modified/middle clicks fall through to the href. Owns the shared NavigationArrow pair (single-step or pair-step hrefs, `relative z-20` so it always stacks above QuranSafha's absolutely-positioned decoration layers), renders two QuranSafha instances (right=odd/leftPage=even) with gap-0 between them on a static `.fq-spread` row. The single-vs-double DISPLAY is CSS-driven, not JS: it marks the non-current card `.fq-safha-partner`, and globals.css (keyed on `html[data-safha-view="double"] .fq-spread` at lg) reveals the partner + applies the width cap + drops the compensate margin — correct at first paint pre-hydration (ADR 0013 Addendum 4). `useIsLgUp`+view survive ONLY to pick the arrow href (pair-step vs single-step). No longer publishes spread geometry — the `useSpreadMetrics` hook and `--fq-spread-width`/`--fq-spread-center` CSS custom properties were retired when the desktop recitation bar moved to a viewport-anchored vertical rail (≥1367px) that needs no spread position data
      QuranSafha               — client shell: handles word selection, mark state, scroll; accepts grantId (undefined = own mushaf); `lines`/`pageMetadata` are NULLABLE — the card renders its loading state from the page number alone rather than through a separate skeleton component (a duplicate drifts from the layout it imitates; ADR 0034), with the shimmer overlay triggered by `!fontReady || !hasContent` so the content wait and the font wait read as one continuous state instead of two blanks. The header is the card's ONLY content-dependent dimension (the text area is `flex: 1 1 0%`; the card width is floored by the worst-case line-width formula), so juz and the surah glyph fall back to a non-breaking space — leave them empty and the header grows when the JSON lands, shrinking the text area and shifting every skeleton line under it; reads QuranMushafContext — sets the container fontFamily from the active edition (`edition.fontFamily(page)`) and adds the `.fq-tajweed` marker class when the edition uses colour glyphs (selects the themed @font-palette-values rule in globals.css, ADR 0023); no decorative frame — plain bg-card + shadow, square corners; 4 offset "stacked pages" layers in the markup, but only 2 visible below 1367px — the deeper pair carries a bare `hidden` (not `hidden md:block`) and is revealed only by the dark ≥1367px block in globals.css, so tablet and mobile keep the 2-sheet look while desktop dark reads as a thicker block (md+, `bg-card dark:bg-muted` inline classNames — white in light/gold at every width, and in dark theme too outside the reader; a `!important` CSS override in globals.css recolors them to `var(--mushaf-paper)`/`var(--mushaf-edge)` for dark theme specifically at ≥768px in the reader, matching the actual page's paper tone instead of a generic card fill — see dark-theme-mushaf-unification.md Phase 2 — + thin border edge for real contrast, small offset, pointer-events-none so they never intercept clicks); stackPeekSide prop ("left"/"right", default "left") controls which side the stack peeks toward and doubles as a left-page/right-page indicator even in single-page view (always static per pair position, not spread-state-dependent); compensateStackGap prop (default false) tags the card `.fq-compensate-l`/`.fq-compensate-r`; globals.css then reserves a physical 9px margin on the SAME side as stackPeekSide (for the stack's ~9px protrusion) at md+ and removes it only when the spread actually shows both pages — so single-page display keeps both nav arrows equidistant. QuranSpread passes it for both cards; standalone QuranPage leaves it false (no `.fq-spread` ancestor → unaffected). Exposes `--fq-word-base`/`--fq-line-gap-base`/`--fq-heading-base` inline so the double-view width cap (the `html[data-safha-view="double"] .fq-spread` rule in globals.css, ADR 0013 Addenda 3–4) can shrink the reading font when two pages would overflow the viewport width. Does NOT re-group lines: `lines` already arrives grouped by the active edition's own line numbers AND composed from that edition's page assignment (ADR 0033). The previous client-side `activeLines` re-grouping mixed one edition's page composition with another's line numbers, which silently rendered words from the wrong page — never reintroduce it. Derives surah banner positions from `line_number` gaps in `lines`: missing slot numbers (1–15) are grouped into consecutive gap runs; each run is classified by looking at the first word after (start/mid gap) or last word before (end gap) — gap size + surah bismillah status determines whether to render SurahBannerLine, BismillahLine, or both. Pages 1–2 skip this gap-detection path entirely and use a fixed 15-slot template instead (Addendum 10, Trello #135): BlankLine at slots 1–3/5/trailing, SurahBannerLine always at slot 4, BismillahLine at slot 6 when the surah has one, content re-sequenced to start right after. Renders SurahBannerLine / BismillahLine / BlankLine local helpers as direct children of .fq-quran-safha (so flex spacing counts them as real slots); passes suppressInlineHeaderForSurahId to the QuranLine immediately after each start/mid banner (or the pages 1–2 template's first content line) to prevent double-rendering of the inline combined heading block. SurahBannerLine's decorative frame is `app/surah-frame.svg` — the KFGQPC band, glyph U+E000 extracted losslessly from QUL's `quran-common.ttf`, a single `currentColor` fill driven by `--mushaf-ornament` (one colour role; the old `--surah-frame-line`/`--surah-frame-gold` tokens and their per-theme/per-band overrides are gone). Its layout slot is `1em` like any other line while its ink is ~1.81em: the SVG is absolutely centred at `width: var(--fq-surah-frame-w, 100%); height: auto`, so it spans the text column, overflows into the inter-line gaps, and contributes zero layout height. The frame's own box is `QURAN_MAX_LINE_WIDTH_RATIO` em (14.42, the measured widest line) with `maxWidth: 100%` and `mx-auto` — matching the text block, not the card's content box; `w-full` made it span the whole page on mobile/tablet where the font caps before lines fill the card (ADR 0011). `height` must stay `auto` — a hardcoded `em` height stretches the art (DECISIONS.md); shrink `--fq-surah-frame-w` if clearance is ever needed
        QuranLine              — one line of the page; accepts optional suppressInlineHeaderForSurahId prop — when set and matching the line's surah, suppresses the inline 2-slot glyph+bismillah block (QuranSafha has already rendered standalone slots for it); mid-page surahs (prop unset or non-matching) keep the existing inline block unchanged
          QuranWord            — single word; click triggers mark flow; carries `data-fq-word={word.location}`, which is how recitation word-level highlighting finds it to classList-toggle directly without React re-renders — it does NOT consume RecitationContext at all, and that is what keeps a context ticking per recited word from re-rendering the whole word tree (ADR 0021 and its 2026-08-03 addendum, which replaced the old `registerWordRef` ref registry: one location maps to several live nodes because the pager mounts the same page in two panels, so a one-element-per-location map highlighted a hidden copy — Trello #182); receives the spot's mark `category` (resolved by QuranLine: word `location` first, else verse `verse_key`) and applies the derived translucent highlight (ADR 0024/0025) — highlight only, the comment is not shown on the page; renders `word.glyph` — the active edition's glyph string, already resolved from code_v1/code_v2 at JSON-generation time, so the render path has no glyph column to pair wrongly with a font (ADR 0033)
```
