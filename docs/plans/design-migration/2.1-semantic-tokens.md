# 2.1 — Semantic tokens

**Type:** feature
**Date:** 2026-08-21
**Status:** implemented
**Parent:** [INDEX.md](INDEX.md) · **Issue:** #360 · **ADR:** [0047](../../architecture/adr/0047-adopt-reader-lab-design-language.md)

## Summary

Express the design language as semantic tokens in the existing theme blocks, so every screen inherits it without being individually rewritten. This is the load-bearing subtask of the programme: everything in Phases 3–5 is mostly *consuming* what this defines.

## Approach

The language introduces four things the shadcn token set has no name for. Each becomes a small named family, defined in **all four** blocks — `.theme-light`, `.theme-gold`, `.theme-dark`, `.theme-dark.dark`:

1. **Accent roles** — the split between identity/metadata and live state. `--primary` already exists and keeps the state role; identity needs its own token family rather than reusing the reader-only mushaf gold, which is scoped to the page.
2. **Atmosphere** — the light source and the vignette, as tokens rather than hard-coded gradients, so a screen can opt in without redeclaring the gradient.
3. **Control treatment** — the inert-vs-live distinction: the well surface, the inert foreground, the live foreground, and the shared focus ring.
4. **Elevation ladder** — the shared depth rule, with per-theme values. Dark's values carry lift with face and rim; light and gold's carry a real cast.

`--radius` stays. Existing tokens are retuned in place rather than renamed — a rename would touch all 81 components for no visual gain.

**Contrast is re-derived for every touched pair.** The current blocks carry measured derivations in their comments, including an explicit "no single lightness satisfies both" for dark's `--primary` / `--accent-foreground` split. Any token change invalidates those. Record the new measurements in the same style, in place.

## Decision Tree / Algorithm

| Condition | Action |
|---|---|
| The language needs a colour shadcn already names | Retune the existing token's value. Do not add a synonym. |
| The language needs a role shadcn cannot express | Add a semantic token, defined in all four blocks. |
| A token would be defined in only some blocks | Not allowed — a missing token silently falls back and flattens that theme (ADR 0032). |
| A pair's contrast drops below WCAG AA | Retune until it clears, and record the measurement. |
| A rule would need a per-theme copy | Change values, not rules. |
| `globals.css` passes ~2600 lines | Decide the restructure (below) and record it. |

**Deferred decision this subtask must resolve and record:** `globals.css` is 2186 lines with heavy per-theme conditionals. Either it grows, or it splits into token / reader / chrome files. Decide with evidence — measure the file after the token families land — and record the reasoning in `Decisions Made`, whichever way it goes.

## Verified Test Cases

| Case | Required outcome |
|---|---|
| Every new token | Defined in all four theme blocks. Grep confirms four occurrences each. |
| Dark `--primary` / `--accent-foreground` | Both still clear WCAG AA against their backgrounds; new measurements recorded in the comments. |
| Gold theme, every new token | Defined and legible against parchment. Gold has no baseline coverage, so verify by eye and by pixel sampling. |
| An unmigrated screen after this lands | Still renders coherently. Retuned tokens shift it; nothing breaks. |
| Atmosphere tokens on a screen that has not opted in | No visual change — the tokens are inert until consumed. |

**Result.** 21 new tokens, 72 defined per theme (was 51), all three blocks, verified by resolving every one in a running browser rather than by grepping the source. Home, reader and marks render in all three themes with no console errors. `tsc` clean.

### Contrast, before → after

| Theme | Pairs below AA before | after |
|---|---|---|
| light | 1 | 1 |
| gold | **7** | 1 |
| dark | 3 | 3 |

Gold's seven failures were the shipped state, not something this subtask introduced — `--primary-foreground` on `--primary` measured **3.41:1** on every button in that theme. Moving the state accent to emerald (which the language requires for its own reasons) fixes six of them: primary-foreground 3.41 → 6.59, accent-foreground 2.74 → 5.36, and the four `--gold`/`--primary`-on-surface pairs.

One pair was introduced and fixed in place: light's `--control-inert` measured 4.48:1 on `--chrome`, under AA by 0.02; 42% lightness measures 4.87:1.

### Pre-existing AA failures NOT fixed here

Measured, recorded, deliberately out of scope — each needs a foreground *and* background co-designed, which is 3.1's work on the primitives that consume them:

| Pair | light | gold | dark |
|---|---|---|---|
| `--destructive-foreground` on `--destructive` | 4.26 | 4.27 | 3.50 |
| `--primary` as text on `--background` | — | — | 3.74 |
| `--primary` as text on `--card` | — | — | 3.48 |

Dark's `--primary`-as-text pair is the "no single lightness satisfies both" tension its own comment already records: raising it to clear 4.5:1 as text drops white-on-primary button contrast below AA. The migration largely dissolves this rather than solving it — ornament and metadata move to `--gold`, so `--primary` stops being text — but 3.1 must confirm that rather than assume it.

## Decisions Made — the two deferred questions

### `.theme-dark.dark` is deleted; the contract is three blocks, not four

Measured before touching it: the two dark blocks were **byte-identical across all 51 tokens** — no token unique to either, no differing value. And `.theme-dark.dark` can never match without `.theme-dark` also matching, because `use-theme.ts` and the pre-paint script always add `dark` and `theme-dark` together and remove them together. It resolved to nothing, while doubling the edit cost of every future token and creating a standing "defined in 3 of 4 blocks" failure mode — precisely the failure ADR 0032 warns flattens a theme silently.

Removing it deleted 96 lines and turned this subtask's own riskiest constraint ("every token in all four blocks") into a smaller one. `.dark` itself is untouched, so Tailwind's `dark:` variant is unaffected.

### `globals.css` is NOT split — decided, not deferred again

The file is 2,889 lines after this subtask. It stays one file, for three reasons, and the decision is revisited after 5.1:

1. **Source order is load-bearing here.** This file is a single `@layer base` block that loses to Tailwind's utility layer at equal specificity, so it leans on `!important` throughout — and ties between two `!important` rules of equal specificity are resolved by source order alone. Subtask 0.3 shipped a real bug from exactly this: a band override placed above the rule it was meant to beat rendered two unreadable columns at 375px. Splitting into files reorders everything at once, mid-migration, with no test that would catch a silent loss.
2. **The cheaper win was taken instead.** Deleting the duplicate dark block removed 96 lines and an entire class of bug, for none of that risk.
3. **37% of the file evaporates on its own.** The reader-lab block is ~1,050 lines and is deleted wholesale when the lab is retired at the end of the programme. Splitting now would mean designing a file layout around a section that is about to disappear.

Revisit after 5.1, when the lab is gone and the source-order dependencies are known rather than guessed.

### Identity lives on `--gold`, not a new family

The plan called for a new token family, on the grounds that `--gold` is the reader-scoped mushaf gold. It is not: the reader's ornament colour is `--mushaf-ornament`, and `--gold`/`--gold-muted` turned out to have **zero consumers** — no `var(--gold)` anywhere in CSS, no `text-gold`/`bg-gold` in any of the 81 components. They were declared in four blocks, wired into `tailwind.config.ts`, and never read.

So this is a scope change on a dead token, not a retint of a live one, and it carries no visual risk. Adding `--identity` alongside would have left two warm families that must be kept equal forever, with one of them a corpse. `--gold` also already has the right name for the role and the Tailwind utilities Phase 3/4 will consume.

## Files to Change

- `app/globals.css` — four theme blocks gain the new families; existing values retuned with re-derived contrast comments.
- `docs/standards/styling.md` — token contract section updated with the new families and the "all four blocks" requirement.
- Possibly new CSS files, if the restructure decision goes that way.

## Constraints

- Every token defined in all four blocks. No partial families.
- Re-derive and record contrast for every touched pair.
- No `--rl-*` token is promoted to `:root` or to a theme block under its lab name. The language arrives under semantic names.
- Depth rules shared; only values differ.
- Verify by sampling rendered pixels in all three themes.
- No component edits in this subtask.

## What NOT to Do

- Do not rename existing shadcn tokens.
- Do not add a token that only one theme defines.
- Do not copy the lab's `--rl-*` block into `globals.css` wholesale.
- Do not adjust a token to fix one screen's appearance — that is a Phase 3/4 problem and doing it here breaks the others.
- Do not defer the `globals.css` restructure decision a second time.

## Decisions Made

- Retune existing tokens in place; add new tokens only for roles shadcn cannot express.
- The identity accent is its own family, not a reuse of the reader-scoped mushaf gold.
- The `globals.css` restructure is decided here, with evidence, and recorded either way.
