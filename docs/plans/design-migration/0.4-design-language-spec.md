# 0.4 — Write the design-language spec

## Summary

Turn everything derived in 0.1–0.3 into a written specification in `docs/design/`. This is the artifact the rest of the programme implements against, and the input to the canon rewrite in 1.1. It records **rules**, not hex values — the values belong to tokens (2.1), and a spec full of hexes goes stale the first time one is retuned.

## Approach

Write `docs/design/design-language.md` covering, for each rule: what it is, why it exists, how it changes per theme, and how it degrades at small screens. A rule that cannot answer all four is not yet derived — send it back to 0.1–0.3.

Sections:

1. **Character** — what the app is trying to feel like, in a paragraph. Supersedes but inherits from the current "manuscript-inspired reading app" framing.
2. **Composition** — folio centring, the proportion cap, symmetric surplus, what owns the optical centre.
3. **Atmosphere** — the light source and the vignette; how each expresses on a dark desk, a light desk, and parchment; when each is dropped.
4. **Depth** — the shared ladder, its ordering, and why dark carries lift with face-and-rim rather than shadow.
5. **Accent grammar** — the two roles, what belongs to each, and the test for deciding which a new element takes.
6. **Control hierarchy** — inert grouped in a well, live outside it brighter; the states a live control must express.
7. **Ornament** — drawn rules and diamonds, where they appear, where they must not.
8. **Structure** — grouped sections with hairline rows; when a card is warranted instead.
9. **Type** — the interface scale; the reading size contract is referenced, not restated.
10. **Motion** — durations, easing, and the reduced-motion contract.
11. **Per-band behaviour** — a table of how every rule above changes at mobile, tablet, desktop.

## Decision Tree / Algorithm

The accent test, which every later subtask will need:

| The element communicates… | Role |
|---|---|
| Who or what this is; where you are; a page's own metadata; ornament | **Gold** — identity |
| Something is happening now, is selected, is on, succeeded, or is live | **Primary** — state |
| Something is wrong | Destructive; never either accent |
| Nothing — it is inert, decorative structure | Neither. A line or a muted tone. |

## Verified Test Cases

| Case | Required outcome |
|---|---|
| A rule in the spec | States its light, gold and dark expression, and its mobile/tablet degradation. |
| A reader picks up the spec cold | Can decide the accent role of a new control without asking. |
| The spec contains a hex value | Only as an illustrative reference with a pointer to the token that owns it. |
| A rule from the lab did not survive light or gold | Recorded as removed, with the reason — not silently dropped. |

**Result.** [`docs/design/design-language.md`](../../design/design-language.md) written: 12 sections, each rule stating its three-theme expression and its per-band degradation. §5 carries the accent test every later subtask applies. §11 carries the per-band table. §12 records the eleven rules that did **not** survive derivation, with the reason for each — including four superseded pre-existing decisions. A closing verification-notes section records the eight measurement errors Phase 0 actually made, because 5.1 will meet them again.

No hex or HSL values appear except as illustrative measured lightness readings; every colour is named by the token that owns it.

Knock-on updates: [`5.1`](5.1-page-face-and-reader.md) gains part (c) — collapsing production's 768–1023px inset band, which the lab overrides and production must follow — and [`INDEX.md`](INDEX.md) gains a Phase 0 outcome section.

## Files to Change

- `docs/design/design-language.md` — new; the specification.
- `docs/plans/design-migration/INDEX.md` — update the phase table if 0.1–0.3 changed the shape of later phases.

## Constraints

- Rules, not values. Hex values appear only as illustrative references pointing at the token that owns them.
- Every rule must state its three-theme expression and its small-screen degradation.
- Does not edit `design-principles.md` — that is subtask 1.1, deliberately separated so the canon rewrite is reviewable on its own.
- Requires explicit user sign-off before Phase 1 opens.

## What NOT to Do

- Do not restate the reading-size contract here; reference ADR 0054 and `quran-rendering.md`.
- Do not include code blocks where a prose rule captures the constraint.
- Do not carry forward a lab rule that failed in light or gold without saying so.

## Decisions Made

- The spec is a new file rather than an expansion of `design-principles.md`, so the derivation and the canon rewrite can be reviewed separately.
- This subtask is a documentation gate: Phase 1 does not open until it is signed off.
