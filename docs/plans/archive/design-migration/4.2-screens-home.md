# 4.2 — Home screen

## Summary

Migrate `/` — the surah list, the continue-reading entry, and the home composition — to the new language. This is the app's front door and the highest-visibility screen after the reader, so it is where the language either reads as intentional or as a reskin.

## Approach

Home is the first real chance to apply the **composition** rules, not just the material ones. The lab's central move was giving the content object the optical centre with symmetric surplus around it; a surah list is a very different object from a folio, so this subtask has to answer what "the content owns the centre" means for a list.

Three specific problems:

1. **The surah list is 114 near-identical rows.** The language's answer to repetition is grouped sections with hairlines, not stacks of cards. Whether 114 rows want juz grouping, or an unbroken hairline list, is a real design decision to make here.
2. **Continue-reading is the one live element on the page.** Under the two-accent grammar it takes `--primary`; everything else on home is identity or neutral. That single distinction should carry most of the page's hierarchy.
3. **Atmosphere on a list screen.** The lamp and vignette were derived for a single centred object. On a full-height scrolling list they may not apply at all — dropping a layer for a screen is a legitimate outcome, and the language spec allows it.

`home-page-design-fixes.md` records contrast work already done here, including the dark `--accent-foreground` derivation. Re-derive rather than assume it survives.

## Decision Tree / Algorithm

| Condition | Action |
|---|---|
| An element tells you where you are or what something is | Identity accent. |
| An element resumes, plays, or is selected | `--primary`. |
| Repetition needs visual relief | Grouped sections with hairlines; not per-row cards. |
| An atmospheric layer has no surround to act on | Drop it for this screen and record why. |
| A contrast pair from `home-page-design-fixes.md` is touched | Re-derive and record the new measurement. |

- Do not change the static surah list JSON contract (`static-surah-list-json.md`).

## What NOT to Do

- Do not give 114 rows individual card surfaces.
- Do not keep an atmospheric layer that has nothing to act on, purely for consistency with the reader.
- Do not restructure home's information architecture; this is a language migration.
- Do not assume the dark `--accent-foreground` derivation survived 2.1's retune.

## Decisions Made

- Home is where the composition rules get their first non-folio application; the answer is recorded back into the language spec.
- Continue-reading is the page's single live element and carries most of the hierarchy.
- Dropping an atmospheric layer for a screen is an allowed, recorded outcome.

## Implementation notes (2026-08-22)

### The three questions the plan raised, answered

**1. What does "grouped sections with hairlines" mean for 114 entries in a six-column grid?**

Neither of the two options the plan offered survived unchanged. A single-column hairline list of 114 rows scans *worse* than the grid does at desktop width — it throws away five columns of usable width to obey a rule about repetition. Juz grouping was rejected too: it imposes a structure the surah list does not have, and 30 headings for 114 entries is barely less noisy than 114 cards.

The answer is a **hairline lattice** (`.fq-section-lattice`): the responsive grid stays, but it becomes one surface whose 1px gaps are painted in the border colour and whose cells carry the card colour. The rule is honoured — one surface, hairlines between entries — without pretending a grid is a list. It also degrades exactly right: at one column it *is* the hairline list, with no separate mobile treatment.

Implemented as a painted gap rather than per-cell borders. Border arithmetic on a grid that reflows between 1 and 6 columns needs to know which cells are on which edge at every breakpoint; the gap does not.

**2. Continue-reading as the one live element.** It now takes `--primary` in the nav. It does not collide with the settings gear, which carries `--control-live` — a neutral raised tone, not the state accent. So home has exactly one emerald element, which was the goal.

**3. Atmosphere on a list screen.** Dropped, and this is the recorded outcome the plan allows. The lamp and vignette were derived for a single centred object with desk visible around it; a full-height scrolling list of 114 entries has no surround for either layer to act on. A vignette with nothing to darken is noise. Neither layer was weakened — both were simply not added.

### Accent-grammar corrections

| Element | Was | Now | Why |
|---|---|---|---|
| Surah number chip | `bg-accent` / `text-accent-foreground` | neutral well fill, `--control-live` | 114 accented chips is an accent that signals nothing. |
| Surah cell | two hardcoded `rgba` casts + `hover:-translate-y-0.5` | flat lattice cell, colour transition only | The casts drew a real shadow on light and gold and **nothing** on dark (ADR 0032). Motion never signals hierarchy. |
| Selected surah cell | `bg-primary/10 border-primary/30` | `bg-primary/10` | Selected is state, so `--primary` is right; the border was redundant once the lattice supplied one. |
| RubList juz heading | `text-primary`, bold | overline treatment, `text-gold` | Which juz you are in is *where you are* — identity. |
| Continue-reading | `text-muted-foreground` | `text-primary` | Resuming is the one genuinely live thing in the chrome. |

### On `home-page-design-fixes.md`

That plan's dark `--accent-foreground` derivation was for the surah-number chips, which no longer use `--accent` at all. The pair is not "assumed to survive" — it is **no longer consumed on this screen**, so there is nothing left to re-derive here. If `--accent` returns to home later, the derivation has to be redone against 2.1's retuned tokens, not restored from that plan.

### Verified

- `/en` renders with no page errors in light and dark; screenshots show the lattice reading as one inventory rather than 114 objects, with Continue Reading the only accent in view.
- Surah name direction (`homepage-surah-name-direction.md`) untouched — the RTL/LTR branch in `SurahListItem` was not modified.
- The static surah list JSON contract was not touched.

### Not done here

`SurahList` is also the reader sidebar's body (`activeSurahId`), so the lattice applies there too. That surface is chrome-adjacent and gets its final pass in 5.1 with the reader; nothing here depends on it looking finished.
