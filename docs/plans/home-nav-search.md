# Home Page Navigation Search (surah name, juz, page)

**Type:** feature
**Date:** 2026-08-25
**Status:** implemented
**Issue:** [#363](https://github.com/furqan-app/web/issues/363) (part of epic #361; sibling #362 sidebar filters is out of scope here)

## Summary

Add a navigation search field to the statically rendered home page. One input, sitting directly above the surah grid and scrolling normally with the page, that live-filters the 114-card grid by surah name (Arabic + English) or exact surah number, and parses numeric queries (plain digits, `juz`/`جزء`/`page`/`صفحة` prefixes, Eastern Arabic numerals) into "Juz N · starts p. P" / "Page N" jump rows that navigate to the reader. Verse-text search stays exclusively in the global nav SearchBar overlay. Everything is client-side over already-loaded static data — no new API endpoints.

## Approach

- New client component `HomeSearch` owns query state and renders: field → jump rows → result count / range hints / zero-state → filtered `<SurahList>`.
- `app/[locale]/page.tsx` wraps `HomeContinueReadingCard` + `HomeRecommendedSurahs` + `HomeSearch` in one client boundary (`HomeSearchSection`) so all three react to one query string. Initial state is idle so SSR output matches first paint (no hydration mismatch); hero stays a server-rendered sibling.
- While a query is active: continue-reading card and recommended chips are hidden; hero + field + results remain. Clearing restores everything.
- Juz→start-page resolution uses a new committed static JSON `public/quran/juz-starts.json` (30 rows: `{ juz, verse_key, defaultPage }`) generated by a manual script from the rubs table (rows where `rub_number % 8 === 1`, mirroring RubList's `Math.ceil(rub_number / 8)` grouping). Rows display `defaultPage` instantly; the active edition's page resolves via the existing `useVersePages()` hook (ADR 0033 — page numbers are meaningless without an edition), fetched lazily only once the query first expresses a juz intent.
- Jump navigation reuses the established home→reader pattern from `HomeRecommendedSurahs`: `Link href={basePath}/{page}` with `jumpTo` short-circuit when a reader is mounted (never true on home today, kept for safety).
- Arabic matching folds hamza-on-alif forms (أ إ آ → ا) on **both** sides at compare time, client-side only. This deliberately diverges from the global overlay's strict chapter search (DECISIONS.md documents that mismatch as accepted *there* because it is an API `contains` over DB columns; here both sides are in-memory strings, so folding costs nothing and fixes the mismatch where the user sees results shrink).

## Decision Tree / Algorithm

Per keystroke, synchronous (no debounce):

1. Trim. Fold Eastern Arabic digits (`٠-٩` U+0660–0669) and Extended (`۰-۹` U+06F0–06F9) to ASCII.
2. Prefix detection, case-insensitive: `juz`/`جزء` → juz intent; `page`/`صفحة` → page intent. Intent holds only if the remainder after the prefix is pure digits; otherwise the whole string is text.
3. Grid filter (cards shown):
   - Text: lowercase + hamza-folded substring against `name_simple` OR `name_arabic`.
   - Pure digits ≤114: exact surah-id match (single card).
   - Pure digits >114: no cards.
4. Jump rows (rendered directly under the field):
   - Bare digit N: `Juz N` row if N≤30, plus `Page N` row if N≤604 (each omitted silently when out of range).
   - Prefixed: exactly that row if in range (juz 1–30, page 1–604); out-of-range renders an inline hint under the field ("Juz 1–30" / "Pages 1–604") instead of a row.
5. Render rules:
   - Rows exist → render them above the grid.
   - Cards = 0 AND rows ≥ 1 → collapse the grid region entirely (never show an empty grid beside a hit).
   - Cards = 0 AND rows = 0 AND query non-empty → unified empty state with cross-link: "Looking for a verse? Use Search" (text link only; do not programmatically open the overlay in this task).
   - Cards > 0 → live count ("٢٣ surahs") next to the field.
6. Keyboard: Escape clears the query; Enter activates the first jump row, else navigates to the first filtered card's start page. No autofocus on mount (mobile keyboard slam — critique persona finding).

## Constraints

- Home stays statically generated; `revalidate = 300` untouched; zero network calls on idle mount (verse-pages fetch is lazy-gated on numeric intent).
- `SurahList.tsx` must remain untouched — shared with the sidebar; filtering happens before it receives props.
- Edition-aware pages only via `useVersePages` (ADR 0033); `defaultPage` is both the display fallback until the map loads and the permanent offline fallback.
- i18n placeholder rule (docs/standards/i18n.md): interpolated keys (`resultsCount`, `juzRow`, `pageRow`) go through next-intl's `useTranslations(namespace)` directly with pre-converted `toLocaleNumeral` strings — never the project wrapper, never `.replace()`.
- Verify `app/sw.ts` runtime caching already covers this JSON the way it covers `verse-pages/{id}.json`; if its matcher enumerates exact paths, extend minimally so jumps resolve offline. Do NOT add juz-starts.json to `globPublicPatterns` (would sweep it into install-time precache for every visitor).
- Generator output committed once; regenerate manually only after a Quran reseed (established convention).
- Parser lives in pure utils with unit tests before UI wiring.

## What NOT to Do

- No debounce — the overlay's 500ms exists for network payload reasons; filtering 114 in-memory rows is synchronous.
- Never auto-navigate on typed digits — suggestions activate only on click/tap/Enter.
- No min-length gate on the filter — the DECISIONS cap+min-length pattern governs API endpoints; none are added here.
- Do not apply verse-search's query-only hamza normalization to `name_arabic` and call it done — the fix here folds BOTH sides in memory; do not touch `/api/search/*` or ADR 0007 semantics.
- Do not add `getRubs()` to the home server component (240 rubs incl. verse words into every visitor's static payload).
- Do not hardcode juz→page numbers without the `verse_key` escape hatch (breaks non-default editions).
- Do not autofocus the field on mount.
- Do not open the global SearchBar overlay programmatically from the empty state — text cross-link only (overlay trigger/state is owned elsewhere).
- Do not restyle chips/resume touch targets or promote headings here — explicitly deferred.
- Do not make the search bar sticky (`position: sticky` under the nav) — tried and rejected in live review: the pinned bar is shorter than the card rows behind it, so card content showed through around its edges; the user explicitly declined sticky positioning (2026-08-25).

## Decisions Made

- Scope: #363 only; epic sibling #362 gets its own plan later.
- Interaction model: hybrid tree confirmed — bare digits surface surah-N card AND juz/page rows together; prefixed queries are jump-only.
- Placement: between recommended chips and grid, scrolling normally with the page. Originally planned sticky under the nav; **rejected in live review** — while pinned, taller card rows showed through around the bar's edges, and the user declined static positioning entirely (2026-08-25).
- Filtering focus: hide continue-reading + recommended while a query is active; hero persists.
- Juz data: static `juz-starts.json` via manual generator (ADR 0028 convention), edition-corrected client-side through `verse-pages`.
- Hamza folding on both sides, client-side only — documented divergence from overlay chapter search; DECISIONS.md Search section gets a one-line amendment during implementation.
- Remediation: minimal (aria labels + dead-class removal in scope); touch targets/h2/colophon deferred to a future issue.
